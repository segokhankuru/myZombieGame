# /data-schema <domain>

Phase 2. Owner: `systems-designer` (the schema) and `tools-programmer` (the importer).

This is the skill that answers "can this studio configure the games it builds". After it
runs, every number in the domain is a one-line JSON edit that flows into the engine
automatically.

---

## 1. Establish the surface

From `design/systems/SYS-*.md` tunable tables, or from `/economy` output if it has run.

For an **existing project**, the surface is discovered instead: grep for serialized
numerics in the domain's scripts.

```
Grep: \[SerializeField\][^;]*\b(float|int)\s+\w+\s*=\s*-?\d
```

Every hit is a candidate. Present them and ask which are tunables and which are
engineering constants. This is usually the most valuable twenty minutes of an onboarding.

## 2. Schema - `systems-designer`, one call

```
<the tunable table, or the discovered serialized fields with their current values>
<the relevant SYS-* intent section>

Task: write the JSON Schema for domain <name>.
- Every key gets a type, a range, and a description saying what the PLAYER experiences
  outside that range.
- Units in key names: patienceSeconds, not patience.
- additionalProperties false - the schema is the contract.
- No computed values. If B is always A x 2, keep A only.
- Group related keys into objects. Flat files of forty keys stop being readable.

Output the schema and a balance file carrying the current or proposed values.
```

## 3. Importer - `tools-programmer`, one call

Runs in parallel with step 2 only if a schema already exists; otherwise chain it.

```
<the schema>
<.claude/docs/config-protocol.md, embedded - sections 1, 4 and 5>

Task: the config pipeline for domain <name>.
1. A generated ScriptableObject class in Assets/_Project/Code/Systems/Config/Generated/,
   marked <auto-generated>, read-only properties, [Range] from the schema.
2. An editor importer that reads config/balance/<name>.json into
   Assets/_Project/Config/<Name>Config.asset. Idempotent. Unknown key is an error.
   Missing required key is an error naming the schema path.
3. A menu command and a static method CI can call.
4. An EditMode test that loads the config and asserts every required key is present.

The runtime reads the ScriptableObject, never the JSON. The importer is the only writer
of the .asset.
```

## 4. Verify - not optional

```powershell
.claude\tools\config-validate.ps1 -Domain <name>
.claude\tools\unity-log.ps1 -Errors
```

Both must be clean. Then run the importer once and confirm the `.asset` appears. A
pipeline that has never been run is a pipeline that does not work.

## 5. Migrate the code (existing projects)

If step 1 discovered hardcoded values, the story is not done until they are gone. List
the call sites and either fix them here or file a story per file. Leaving both a config
key and a serialized field is worse than either alone: the two will disagree and nobody
will know which one the game is using.

## 6. Close

```
✓ Domain <name>: <n> keys, schema + balance + importer + ScriptableObject.

Validated: config-validate PASS   Compiles: yes
Migrated: <n> hardcoded values removed from <n> files   <or: none, new domain>

Tune it with:  /tune <name>
Check it with: /balance-check <name>

▶ Next: /data-schema <next domain>   or   /epics
```

---

## Token note

- **Two agent calls**, parallel when a schema already exists.
- The importer is written once per project, not per domain - later domains reuse it and
  cost one call.
- This is the highest-return refactor available on an existing Unity project: it converts
  every future balance change from an Editor session into a one-line diff.
